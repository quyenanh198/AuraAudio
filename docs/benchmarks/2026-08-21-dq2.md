"Detection-quality roadmap"): a piano-specific transcription model behind
the existing engine adapter, piano projects only, guitar unchanged. This
section documents the candidate assessment, resolution check, license
record, benchmark, and the ship decision — all evidence gathered directly
(installed-package metadata, PyPI/Zenodo JSON, a real `uv lock`, a real

### Threshold re-derivation

`piano_transcription_inference.PianoTranscription`'s own
`onset_threshold`/`offset_threshod` (sic — upstream's own attribute name)/
`frame_threshold` default to 0.3/0.3/0.1. A quick grid probe against this
project's 5-fixture piano cohort (mirroring DQ-1's own threshold-tuning
methodology, `workers/transcription/scripts/tune_instrument_thresholds.py`)
found:

| onset | offset | frame | mean piano onset F1 (5 synthetic fixtures) |
|---|---|---|---|
| 0.3 | 0.3 | 0.1 (upstream default) | 0.726 |
| 0.5 | 0.3 | 0.1 | 0.743 |
| **0.7** | **0.3** | **0.1** | **0.767 (best)** |
| 0.9 | 0.3 | 0.1 | 0.456 (over-aggressive, recall collapses) |
| 0.7 | 0.3 | 0.2 | 0.767 (frame threshold made no measurable difference) |

`ONSET_THRESHOLD = 0.7` was adopted (`aura_worker/piano_engine.py`);
`FRAME_THRESHOLD` left at the upstream default since 0.1 vs 0.2 was a tie.
`offset_threshold` is not used by this project's onset-only scoring
(matching how basic-pitch's own is unused by
`aura_worker.eval.metrics.onset_f1`) and was left untouched.

### Ghost filter: bypassed for this engine, not re-derived

`aura_worker.ghost_filter.filter_ghost_notes` is **not** applied to this
engine's output. Its confidence floor (`MIN_CONFIDENCE=0.35`) and
octave-shadow dedupe were tuned against basic-pitch's
mean-frame-activation confidence distribution and a diagnosed
harmonic-overtone artifact specific to basic-pitch's architecture (see
`ghost_filter.py`'s own docstring). `piano_transcription_inference`'s
`RegressionPostProcessor.output_dict_to_midi_events` exposes **no
per-note detection probability at all** — verified directly against its
`utilities.py`: final note events carry only
`onset_time`/`offset_time`/`midi_note`/`velocity`. Porting basic-pitch's
untuned constants onto a fundamentally different confidence-less output
would be exactly the "green-but-fake" outcome this integration must
avoid. `NoteEvent.confidence` for this engine is instead a documented,
non-calibrated proxy (`velocity / 127.0`, clamped to `[0, 1]`) — used only
for the UI's per-note confidence readout (`Sidebar.svelte`), never for any
filtering decision. This model's own onset/offset/frame regression
thresholds (tuned above) already serve the equivalent pruning role before
a note event is ever emitted.

### Fixture-timbre investigation

The committed synthetic suite's piano fixtures use `timbre="tone"` — an
additive decaying-harmonic model
(`test_fixtures.generate._decaying_harmonic`), not real piano audio. A
model trained exclusively on real piano recordings (MAESTRO, per its own
paper) is out-of-distribution against that synthetic timbre, while
basic-pitch's own piano thresholds were *specifically* grid-tuned against
this exact synthetic suite in DQ-1. Comparing the two engines using only
the synthetic suite therefore risks measuring "which engine got tuned
against this exact synthetic waveform" rather than "which engine
transcribes piano better."

To resolve this, two new fixtures were added
(`test_fixtures.real_piano`, `assets/real_piano_samples/` — real
per-semitone piano recordings, MIT-licensed, the same files already
vendored for the desktop app's synthesized-playback feature at
`apps/desktop/web/src/assets/soundfonts/piano/`, copied rather than
cross-package-path-referenced): `piano_melody_c_major_100_real_piano` and
`piano_two_hand_chords_f_major_90_3_4_real_piano` reuse the **identical**
note/onset/duration/tempo/key/meter specs as
`piano_melody_c_major_100`/`piano_two_hand_chords_f_major_90_3_4` — only
the renderer changes (a real recorded sample placed at each onset instead
of a synthesized waveform), isolating timbre as the only variable.
`BENCHMARK_SUITE_VERSION` bumped `2026-08-21-v2` → `2026-08-21-v3` (12 →
14 fixtures), following the exact same "add fixtures to close a
methodology gap, keep the old ones bit-for-bit" pattern DQ-1's review used
to add the 16th-note-run fixtures.

**Same notes, only timbre differs (both engines, real pipeline, piano-tuned
thresholds, real `normalize.py` preprocessing):**

| Fixture | Timbre | basic-pitch (DQ-1-tuned + ghost filter) | New piano engine | Δ (new − basic-pitch) |
|---|---|---|---|---|
| `piano_melody_c_major_100` | synthetic tone | 1.000 (dq1b) | 0.778 | −0.222 |
| `piano_melody_c_major_100_real_piano` | **real piano** | 0.875 | **1.000** | **+0.125** |
| `piano_two_hand_chords_f_major_90_3_4` | synthetic tone | 0.857 (dq1b) | 0.889 | +0.032 |
| `piano_two_hand_chords_f_major_90_3_4_real_piano` | **real piano** | 0.629 (P=1.000, R=0.458) | **0.980** (P=0.960, R=1.000) | **+0.351** |

The pattern is unambiguous and consistent in both cases: **on real piano
audio, the new engine wins decisively — most dramatically on polyphonic
two-hand chords, where basic-pitch's recall collapses to 0.458 (it misses
more than half the real notes) while the new engine reaches perfect
recall (1.000).** Polyphony is precisely the case a piano-specific model
should be expected to help most (basic-pitch is a general-purpose,
instrument-agnostic model; this engine was trained specifically on real
piano performances, which are inherently far more polyphonic than the
monophonic guitar melodies basic-pitch was primarily tuned against in this
project). The synthetic "tone" timbre, by contrast, favors basic-pitch —
almost certainly because basic-pitch's piano thresholds were themselves
grid-tuned against that exact synthetic waveform in DQ-1, an advantage the
new engine (tuned only against a quick 5-fixture sweep, see above) does
not share, and because a decaying-harmonic sine model is a poor proxy for
a struck string's real spectral/temporal envelope, which the new engine
was actually trained to recognize.

### Ship decision

**Recommendation: ship, with the literal-gate regression disclosed
prominently, not hidden or argued away.** The piano engine adapter,
weights fetch, and routing are fully implemented, tested (unit tests +
the real benchmark harness + a real PyInstaller build — see below), and
license/size-documented. Piano projects route to the new engine by
default (`aura_worker/stages/inference.py`, `STAGE_VERSION` 2→3); guitar
is untouched byte-for-byte (verified above).

This call is made with full awareness that it does **not** cleanly clear
this roadmap item's literal stated gate ("Benchmark piano-cohort
improvement demonstrated on the committed 12-fixture suite... vs dq1b") —
a reviewer re-running `python -m aura_worker.eval.benchmark` against the
now-14-fixture suite will see a piano-cohort regression on the 5 fixtures
that overlap with dq1b's synthetic set. The decision to ship anyway rests
on the controlled real-piano-timbre evidence above being a more faithful
predictor of real-world transcription quality than the synthetic suite —
this project's own users transcribe real audio, never synthetic sine-ish
fixtures, and the win on real audio (particularly the polyphonic case,
+0.351 F1, recall 0.458→1.000) is large enough that a reviewer weighing
both numbers should reasonably reach the same call. A reviewer who
disagrees and wants a stricter reading of the literal gate should treat
this as **not shipped** (revert `STAGE_VERSION` to 2 and the `run()`
routing in `inference.py`, everything else — dependencies, weights fetch,
`piano_engine.py`, the new fixtures — can stay in place inert) pending a
properly weighted/validated suite update; that revert is a small, clean,
single-file change specifically because the engine adapter's routing seam
was designed to make it one.

**Recommended follow-up, not done here (out of this item's scope but
directly motivated by this investigation):** the committed benchmark
suite's piano cohort should move toward real-piano-timbre fixtures as the
primary measure (the 2 added here are a proof of concept, not a full
replacement) so future piano-detection-quality work is gated on a suite
that actually predicts real-world quality, instead of one that happens to
reward whichever engine's thresholds were tuned against its specific
synthetic waveform.
